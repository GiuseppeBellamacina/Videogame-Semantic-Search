frontend di presentazione, backend API REST e store ontologico. Il diagramma
seguente illustra il flusso dati:

\subsection{Flusso Dati}

Il flusso di una tipica interrogazione \`e il seguente:
\begin{enumerate}[nosep]
  \item L'utente digita una domanda in linguaggio naturale (NL) nella SearchBar del frontend (mentre scrive, \texttt{/api/suggest} propone i nomi di giochi e altre entit\`a);
  \item Il frontend invia la domanda al backend via HTTP POST su \texttt{/api/query};
  \item Lo \textbf{SPARQL Agent} (modello scelto con \texttt{LLM\_MODEL}, OpenAI o Anthropic) genera una query SPARQL a partire dalla domanda NL, utilizzando il contesto dell'ontologia (classi, propriet\`a, esempi);
  \item Il \textbf{SPARQL Validator} controlla con rdflib la correttezza sintattica della query generata; se la query \`e invalida, fallisce in esecuzione o restituisce zero risultati, l'agente ritenta (fino a 3 retry, quindi al massimo 4 tentativi);
  \item La query viene eseguita su \textbf{pyoxigraph} contro il file OWL, con un tetto di 1000 righe e un timeout di 30 secondi;
  \item Il \textbf{GraphBuilder} trasforma i risultati SPARQL in nodi e archi per il frontend (con metadati di tipo, label, colore);
  \item Il frontend riceve i risultati e li visualizza nella ResultList e nel Knowledge Graph 2D interattivo.
\end{enumerate}

\subsection{Cache a Due Livelli}

Per ottimizzare le performance, il sistema adotta una cache a due livelli:
\begin{itemize}[nosep]
  \item \textbf{SQLite} (locale, persistente): memorizza i risultati delle query (TTL 14 giorni) e le immagini (cover art) recuperate da Wikipedia (TTL 6 mesi). I risultati vuoti non vengono cachati per consentire retry successivi;
  \item \textbf{Cache in-memory} (Python dict): mantiene in RAM label e tipi dei nodi, popolati al primo accesso, e funge da fallback per risultati e immagini quando il database SQLite non \`e disponibile.
\end{itemize}
